# FHIR-2101: Lab results not showing correctly in the patient app

**Reported by:** Patient Portal team
**Symptom:** "Patients say their CBC results aren't showing. The ORU → FHIR channel shows the messages as sent."

## Investigation
- Mirth status was **SENT**. That only means the HTTP request was delivered, not that the data is right, so the FHIR server was checked directly.
- `DiagnosticReport?subject=Patient/…` returned the CBC report with 3 linked results: the report itself was fine.
- `Observation?subject=Patient/…` returned **4** Observations for 3 OBX lines. One was a blank platelet result: code `777`, no value, empty narrative.

## Reproduction (order LAB8001)
| Message | Platelet OBX | Result on the server |
|---|---|---|
| A: malformed | `OBX\|3\|NM\|777^^LN\|\|\|\|…` (truncated code, no value) | Observation `LAB8001-777`, **no value** |
| B: corrected | `OBX\|3\|NM\|777-3^Platelets…\|\|310\|…` | **second** Observation `LAB8001-777-3`, value 310 |

The patient now had two platelet results, one blank. The DiagnosticReport pointed only at the good one, but any app searching the patient's Observations showed both.

## Root cause
1. **No validation:** the OBX loop created an Observation even when OBX-3 or OBX-5 was empty.
2. **Fragile identifier:** the Observation identifier was `filler order + OBX-3 code`. The malformed code produced a different identifier, so the corrected resend created a new Observation instead of replacing the bad one.

## Fix (ORU → FHIR transformer, OBX loop)
```javascript
var setId = obx['OBX.1']['OBX.1.1'].toString();
if (code == '' || value == '') {
    throw 'OBX ' + setId + ' is missing a code or value';
}
...
identifier: [{ system: 'http://mirthlab.example.org/result', value: fillerID + '-' + setId }],
...
request: { method: 'PUT', url: 'Observation?identifier=http://mirthlab.example.org/result|' + fillerID + '-' + setId }
```
- Malformed messages now **error** in Mirth (the lab gets an AE) and nothing is written to the FHIR server.
- The identifier uses **OBX-1 (set ID)**, which stays the same when a result is corrected.

Rejecting the whole message (instead of skipping the bad OBX) is deliberate: a partial lab report can mislead a clinician more than a late one.

## Verification (order LAB8002, after the fix)
| Test | Expected | Result |
|---|---|---|
| A: malformed message | ERROR, nothing stored | `OBX 3 is missing a code or value`; `identifier=…LAB8002-3` → total **0** |
| B: final result | 1 Observation | total **1**, Observation 870849, 285 10*3/uL, status final, version 1 |
| C: corrected result (OBX-11 = C) | same Observation updated | total **1**, **same id 870849**, 292 10*3/uL, status **corrected**, **version 2** |

## Lessons
- **SENT is not success:** check the target system, not just the engine status.
- The reported problem ("results not showing") was not the real problem (an invalid extra result).
- Identifiers used for upserts must stay stable across corrections.
